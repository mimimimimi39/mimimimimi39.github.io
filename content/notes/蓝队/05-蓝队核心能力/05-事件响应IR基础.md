## 1. 什么是事件响应

事件响应（Incident Response, IR）是对安全事件进行**准备、检测、分析、遏制、清除、恢复、复盘**的系统化过程。

目标：

- 控制影响范围
- 保护证据
- 恢复业务
- 找到根因
- 防止复发

> 事件（Incident）与事件（Event）不同：日志中的每条记录是 event；对组织造成或可能造成影响的安全事件才是 incident。

---

## 2. 常见事件类型

- 恶意软件/勒索/挖矿
- 主机失陷/Webshell
- 账号泄露/内部威胁
- 数据泄露
- 钓鱼/社工
- 网络攻击/DDoS
- 云配置错误/云账号劫持
- 供应链事件
- 合规/隐私事件

---

## 3. NIST 事件响应生命周期

NIST SP 800-61 的四阶段（r2，仍被广泛使用）：

```text
1. 准备（Preparation）
2. 检测与分析（Detection and Analysis）
3. 遏制、根除与恢复（Containment, Eradication, and Recovery）
4. 事后活动（Post-Incident Activity）
```

> NIST SP 800-61r3（2025）更强调与 CSF 2.0 的风险管理融合，并引入持续改进理念。传统四阶段仍是面试与实战的通用语言。

### 3.1 准备

- 资产清单与业务影响分析
- 日志与监控
- 应急预案与 Playbook
- 团队与联系人
- 工具与取证包
- 备份与恢复演练
- 法律与合规
- 培训与演练

### 3.2 检测与分析

- 告警、用户报告、情报
- 验证真实性
- 确定影响范围
- 建立时间线
- 判断事件类型与级别
- 保存证据

### 3.3 遏制、根除、恢复

- 短期遏制：隔离主机、封禁 IP、禁用账号
- 长期遏制：加固、分段、监控
- 根除：删除恶意文件、修复漏洞、重置凭据
- 恢复：恢复业务、验证、持续监控

### 3.4 事后活动

- 复盘会议
- 时间线与根因
- 改进项与责任人
- 更新 Playbook/规则
- 度量与汇报

## 4. SANS PICERL 模型

| 阶段 | 内容 |
|---|---|
| Preparation | 准备 |
| Identification | 识别 |
| Containment | 遏制 |
| Eradication | 根除 |
| Recovery | 恢复 |
| Lessons Learned | 经验教训 |

> NIST 与 SANS 本质一致，只是阶段划分不同。面试能说清即可。

## 5. 团队与角色

| 角色 | 职责 |
|---|---|
| 事件指挥官（IC） | 总体协调、决策 |
| 分析师 | 调查、取证、研判 |
| 遏制/处置人员 | 隔离、清除、恢复 |
| 沟通负责人 | 内部/外部沟通 |
| 法务/合规 | 法律与监管 |
| IT/业务 | 系统与业务支持 |
| 公关 | 对外声明 |
| 管理层 | 资源与决策 |

小团队可以一人多角，但职责要明确。

## 6. 沟通

### 6.1 沟通原则

- 及时、准确、简洁
- 事实与推测分开
- 定期更新
- 明确下一步与负责人
- 保护敏感信息

### 6.2 沟通对象

- 技术团队
- 管理层
- 业务部门
- 法务/合规
- 客户/监管（按法规）
- 媒体/公关（统一口径）

### 6.3 沟通模板

```text
【事件简报】
时间：
事件：
影响：
当前状态：
已采取措施：
下一步：
需要支持：
```

## 7. 证据保全

### 7.1 证据类型

- 内存
- 磁盘镜像
- 日志
- 网络流量
- 文件样本
- 注册表
- 浏览器数据
- 云审计日志

### 7.2 证据链（Chain of Custody）

记录：

- 谁采集
- 何时采集
- 从哪里采集
- 用什么工具
- 哈希值
- 存放位置
- 谁接触过

### 7.3 注意事项

- 先保存易失数据（内存、网络连接、进程）
- 尽量不直接关机（可能丢失内存证据）
- 写保护磁盘
- 计算哈希
- 备份而非修改原始证据
- 记录所有操作

## 8. 遏制策略

| 策略 | 优点 | 风险 |
|---|---|---|
| 网络隔离 | 快速阻断扩散 | 影响业务 |
| 禁用账号 | 阻断凭据滥用 | 影响用户 |
| 封禁 IP/域名 | 阻断 C2 | 可能误封 |
| 下线服务 | 彻底 | 业务中断 |
| 重置凭据 | 清除访问 | 影响范围大 |
| 全网排查 | 发现其他失陷 | 成本高 |

> 遏制要在「控制影响」与「保留证据/业务连续」之间平衡。

---

## 9. 事件分级

| 级别 | 示例 | 响应 |
|---|---|---|
| P1/紧急 | 核心数据泄露、勒索扩散 | 立即响应、全员 |
| P2/高 | 主机确认失陷、特权账号 | 快速响应 |
| P3/中 | 可疑行为、单点异常 | 工作时间处理 |
| P4/低 | 低风险尝试、信息性 | 记录/批量处理 |

---

## 10. Playbook 示例：主机失陷

```text
1. 确认告警/报告
2. 隔离主机网络（保留管理通道）
3. 保存内存、进程、网络、日志
4. 分析入口、恶意文件、持久化
5. 判断影响范围（同账号、同网段、同漏洞）
6. 清除恶意内容，修复入口
7. 重置相关凭据
8. 恢复主机/重装
9. 持续监控
10. 复盘与改进
```

## 11. 演练

- Tabletop（桌面推演）
- 红蓝对抗
- 钓鱼演练
- 备份恢复演练
- 勒索演练
- 通信演练

> 演练不是为了「好看」，而是发现流程、工具、人员的短板。

### 11.1 Tabletop 示例

场景：财务人员收到「发票」附件，打开后机器变慢，EDR 告警 PowerShell 外连。

讨论问题：

1. 最先做什么？是否需要隔离？
2. 需要保存哪些证据？
3. 如何判断影响范围？
4. 何时升级、通知谁？
5. 如何清除、恢复与复盘？

## 12. 指标

- 事件数量与类型

- 恢复时间
- 复发率
- 改进项完成率

## 13. 法律与合规

- 授权与范围
- 证据合法性
- 个人信息保护
- 数据泄露通报义务
- 行业监管要求
- 与执法机关协作
- 不擅自反制

---

## 14. 常见错误

| 错误 | 后果 |
|---|---|
| 直接关机/重装 | 丢失证据 |
| 未隔离 | 攻击扩散 |
| 只看单机 | 漏掉横向 |
| 过早清除 | 无法取证 |
| 不重置凭据 | 攻击者回来 |
| 不修复入口 | 再次失陷 |
| 不写报告 | 无法复盘/合规 |
| 沟通混乱 | 业务/管理层不满 |
