## 1. 什么是 SOC

SOC（Security Operations Center，安全运营中心）是组织集中监控、检测、分析、响应安全事件的团队与平台。

目标：

- **看得见**：资产、账号、日志、流量、漏洞
- **判得准**：告警是否真实、影响多大
- **响应快**：遏制、清除、恢复
- **防得久**：复盘、加固、优化检测

SOC 不是「一个房间 + 一堆大屏」，而是**人 + 流程 + 技术 + 数据**的组合。

---

## 2. SOC 的类型

| 类型 | 说明 | 优点 | 缺点 |
|---|---|---|---|
| 自建 SOC（内部） | 企业自己建设 | 熟悉业务、数据可控 | 成本高、人才难 |
| MSSP（托管安全服务） | 安全厂商代为运营 | 成本低、7×24 | 业务理解弱、沟通链长 |
| 混合 SOC | 自建 + 外包 | 平衡 | 协调复杂 |
| 虚拟 SOC | 远程团队 | 灵活 | 依赖网络与流程 |
| 云 SOC | 云原生安全运营 | 与云集成 | 多云复杂 |

## 3. 组织与角色

### 3.1 三层分析模型

| 层级 | 职责 | 关键能力 |
|---|---|---|
| L1 | 7×24 监控、告警初判、工单、按 Playbook 升级 | 基础网络/系统、告警识别、沟通 |
| L2 | 深入研判、多源关联、定性定级、处置建议 | 日志/流量/ATT&CK、独立分析 |
| L3 | 复杂事件、威胁狩猎、检测工程、带教 | 应急/取证/开发/规则 |

### 3.2 其他角色

- SOC Manager：运营管理、指标、汇报
- 检测工程师：规则开发与调优
- 威胁情报分析师：情报生产与落地
- 应急响应工程师：深度处置
- 安全研发：平台与自动化
- 合规/审计：等保、内审

### 3.3 值班模式

- 7×24 三班倒 / 四班倒
- 白班 + 值班手机
- 跟随业务时区
- 交接班必须书面化

## 4. 核心流程

### 4.1 监控与告警

```text
日志采集 → 解析归一化 → 关联规则 → 告警 → 队列 → 分派 → 研判
```

### 4.2 告警生命周期

| 状态 | 含义 |
|---|---|
| New | 新告警 |
| In Progress | 研判中 |
| Escalated | 升级 L2/L3 |
| Contained | 已遏制 |
| Resolved | 已解决 |
| Closed | 关闭（含误报） |
| False Positive | 误报 |

### 4.3 工单字段

- 告警标题、时间、来源
- 资产（主机、IP、账号、业务）
- 事件类型、严重级别
- 证据（日志、截图、IOC）
- 分析过程与结论
- 处置动作
- 升级/通知对象
- 附件与时间线

### 4.4 升级原则

- 影响核心资产/数据 → 立即升级
- 事件仍在扩散 → 立即升级
- 涉及高管/合规 → 立即升级
- 无法定性 → 升级 L2
- 误报也要记录原因

### 4.5 交接班

```text
本班告警处理情况
未闭环工单
重点资产/业务变更
正在发生的事件
需要下一班关注的事项
```

## 5. 技术栈

```text
数据源：终端、服务器、网络、安全设备、应用、云、身份
采集：Agent、Syslog、API、流量镜像
平台：SIEM、SOAR、EDR、NDR、TIP、UEBA
分析：查询、关联、机器学习、威胁情报
响应：隔离、封禁、禁用账号、工单、通知
```

| 类型 | 代表 |
|---|---|
| SIEM | Splunk、Elastic、Sentinel、QRadar、ArcSight、奇安信、深信服 |
| EDR | Microsoft Defender、CrowdStrike、SentinelOne、火绒、奇安信 |
| NDR | Darktrace、Zeek、Suricata、Arkime |
| SOAR | Splunk SOAR、Shuffle、Cortex XSOAR |
| TIP | MISP、OpenCTI、微步、奇安信 |
| 漏洞 | Nessus、Qualys、OpenVAS |

## 6. 指标体系

| 指标 | 定义 | 用途 |
|---|---|---|
| MTTD | 平均检测时间 | 检测能力 |
| MTTA | 平均确认时间 | 响应效率 |
| MTTR | 平均响应/恢复时间 | 处置能力 |
| 告警量 | 单位时间告警数 | 运营负载 |
| 误报率 | 误报/总告警 | 规则质量 |
| 漏报率 | 未检测到的事件比例 | 覆盖能力 |
| 覆盖率 | 资产/日志/ATT&CK 覆盖 | 建设完整性 |
| 事件复发率 | 同类事件再次发生 | 改进效果 |
| 自动化率 | 自动处置比例 | 成熟度 |

> 不要只追求「告警清零」，要追求「真实事件不漏、误报可控、响应可度量」。

## 7. Playbook 与 Runbook

### 7.1 Playbook

针对某类事件的标准化处置流程，例如：

- 钓鱼邮件
- 勒索软件
- Webshell
- 暴力破解
- 恶意 IP 外联
- 数据泄露
- 账号被盗

### 7.2 Runbook

更偏操作步骤，例如：

```text
1. 确认告警真实性（查看原始日志）
2. 查询资产信息（负责人、业务、重要性）
3. 查询账号信息（最近登录、权限）
4. 查询威胁情报（IP/域名/哈希）
5. 判断影响范围（同网段、同账号、同时间）
6. 执行处置（隔离/封禁/禁用）
7. 记录工单并通知
8. 复盘
```

## 8. SOC 成熟度

| 阶段 | 特征 |
|---|---|
| 1 初始 | 有设备，少量告警，手工处理 |
| 2 基础 | 日志集中，有流程与工单 |
| 3 规范 | 有 Playbook、指标、定期复盘 |
| 4 优化 | 检测工程、自动化、威胁狩猎 |
| 5 引领 | 主动防御、情报驱动、持续改进 |

## 9. 常见问题

| 问题 | 表现 | 改进 |
|---|---|---|
| 告警疲劳 | 每天上万条，无人处理 | 调优规则、降噪、分级 |
| 日志缺失 | 关键事件查不到 | 补数据源、开审核 |
| 流程不清 | 升级慢、责任不明 | 明确 Playbook 与值班 |
| 只盯设备 | 有告警无分析 | 培养分析能力 |
| 不复盘 | 同类事件反复 | 事件复盘机制 |
| 指标单一 | 只看告警数量 | 建立 MTTD/MTTR/覆盖率 |

## 10. 实操

1. 设计一个 SOC 值班表与交接班模板。
2. 写一份告警工单模板。
3. 模拟一条告警，按 L1 流程处理并升级。
4. 设计 3 个 SOC 指标并说明如何采集。
5. 为一个事件类型写 Playbook。
